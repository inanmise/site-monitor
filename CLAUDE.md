# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Site Monitor — full-stack SSL/TLS certificate monitoring system. Spring Boot 4.1 / Java 25 backend serves a React 18 (Vite 5) SPA; PostgreSQL is the system of record. Single deployable: the React `dist/` is served as static content from the Spring Boot jar in prod. Single VERSION file (`./VERSION`) is authoritative for both backend (`pom.xml` uses `${revision}`; the Docker build passes `-Drevision=$(cat VERSION)`, local builds produce `0.0.0-local`) and frontend (`vite.config.js` reads it at build time).

The UI is bilingual TR/EN. **The default language is English** (product decision 2026-10-02): a user with no stored choice sees EN, and a chosen language is kept. The default is read in three places that must agree: `storedLang()` in `i18n/index.jsx`, `dateLocale()` in `i18n/dateLocale.js` (en-GB), and the `X-Lang` header in `api/client.js` (gates: `defaultLanguage.test.jsx`, `client-lang-header.test.js`). The backend `Msg.t` fallback stays `tr` for requests without a header (mails, jobs). Most identifiers, log messages, and admin-panel strings are Turkish — keep i18n keys in sync (see `i18n-parity.test.jsx`).

## Architecture — what you need to know across files

### Single-process deployment, multi-replica safe
Frontend ships **inside** the backend jar (`spring.web.resources.static-locations=file:./frontend/dist/,classpath:/static/`). In Kubernetes the same image runs N replicas, so anything stateful must survive pod death and not double-fire:

- **Sessions (fixed 2026-10-09)**: one switch, `site.monitor.session.store` (env `SPRING_SESSION_STORE_TYPE`): `jdbc` in the `prod` profile → Spring Session JDBC (`spring_session` / `spring_session_attributes`, cookie `SESSION`); `memory` (default, local dev + tests; blank/`none` too) → Tomcat session, `JSESSIONID`. `config/SessionStoreAutoConfigurationFilter` (an `AutoConfigurationImportFilter` in `META-INF/spring.factories`) drops Boot's `org.springframework.boot.session.*` auto-configs unless the switch is `jdbc` — Boot 4 moved them into `spring-boot-session-jdbc` and has no on/off property, and `spring.session.store-type` no longer exists (that is why prod silently ran in-memory from the 3.3.6 → 4.1.0 upgrade on 2026-06-17 until this fix). `service/session/SessionStoreService` reports the REAL store (bean present?) to System Health (`session_store`) and does the startup marker cleanup: memory clears every non-TERMINATED `active_session_id` (unchanged), jdbc clears only markers with no live `spring_session` row. Gates: `SessionStoreRestartIntegrationTest` (login → restart on the same DB → same cookie still 200), `SessionStoreServiceJpaTest`, `SessionStoreAutoConfigurationFilterTest`.
- **Scheduler distributed lock**: `SchedulerService` self-manages a `scheduler_lock` table (insert/expire by `locked_until`). Only one pod runs the hourly cert sweep. Lock TTL = `SCHEDULER_LOCK_TTL_MINUTES` (10). Admin can force-release via `DELETE /api/admin/system/scheduler-lock`.
- **Cluster schedule + sweep leader (2026-10-09)**: `service/schedule/ClusterScheduleService` keeps per-monitor due times (`monitor_check_schedule`, key `<type>:<id>`, claim = CAS UPDATE on `next_due_at`), round claims (`round:<name>`, never released, so uptime/daily/cron rounds run once per cluster) and the sweep leader lease (`lease:sweep-leader`, `site.monitor.scheduler.sweep-leader-ttl-ms` 180 s). Every scheduled sweep that feeds `MonitoringOutageService` starts with `if (!isSweepLeader()) return;` because recovery counters and sibling-DOWN records are per-pod memory — a new monitoring sweep must add the same gate. Graceful shutdown releases the lease; DB failure falls back to local runs. Manual "Check now" never goes through the schedule. **Lease renewal is independent of the sweep threads (2026-10-09):** `startSweepLeaderRenewer` (at boot, only with the cluster store) renews the lease on its own daemon thread every `ttl/3` (`renewSweepLeadership`), so 54 `@Scheduled` jobs filling the 8-thread pool for longer than the TTL no longer hand leadership over; a follower's renewer takes an expired lease. It also installs `MonitoringOutageService.setScheduledResultsFence(this::isSweepLeader)`: SCHEDULED results (and `handleDnsSweep`) from a pod that lost the lease are dropped (manual checks pass; a failing fence is open). Shutdown stops the renewer before releasing the lease. Single pod: identical behaviour. Gates: `SchedulerClusterScheduleTest` (renewer/fence cases), `MonitoringOutageServiceTest.scheduledResultsFence_*`.
- **JPA**: `spring.jpa.open-in-view=false` — entities must be DTO-mapped inside the service transaction; lazy associations after return will throw. Hibernate `ddl-auto=update` is the schema-evolution mechanism (no Flyway/Liquibase).

### Auth — custom interceptor, not Spring Security filter chain
`AuthInterceptor` (registered in `WebConfig`) guards `/api/**`. Login goes through `AuthController`, sessions are HttpSession-based with a remember-me cookie validated by `RememberMeService` (token table: `remember_me_tokens`). Three orthogonal lock states on `AppUser`:
- `lockoutUntil` — temporary progressive lockout (durations: 30s→120s→600s→1800s by default). **Since 2026-09-26 there is no automatic permanent lock** (product decision: an anonymous attacker could permanently lock any account): beyond the last level every further violation repeats the last duration (30 min). Attempts made while locked (`LOGIN_FAILED` with outcome `BLOCKED`) don't count, and the counter uses the canonical username.
- **Unknown usernames (2026-10-09):** a non-existent name climbs the SAME ladder as an active account (`service/lockout/LockoutLadder` is the single source for failures-needed and durations), stored in `login_unknown_lockouts` (all pods agree), so status, body and `wait_seconds` are identical at every level; no `ACCOUNT_LOCKED` audit and no AppUser row for it. A failed local login always burns one BCrypt. Gate: `AuthControllerUnknownLockoutParityTest`.
- `permanentLock` — legacy state from before 2026-09-26 (and any admin-set lock); admin-only release. Nothing sets it automatically any more.
- `mustChangePassword` — while set, only `/api/me`, `/api/me/change-password`, `/api/login`, `/api/logout` are reachable. Don't add bypass paths.
- `active=false` (passive, user decision 2026-10-02) — a passive account can NEVER sign in, by any path. Local password, LDAP/AD bind (checked on the EXISTING row before `provisionFromAd`, which never runs, so the user is not reactivated) and remember-me all return `ACCOUNT_INACTIVE` (login 403, otherwise 401; JSON `code`/`error_code`). The "passive" message is shown only after the credentials are verified; a wrong password keeps the generic 401 (no enumeration). Audit `LOGIN_FAILED` outcome BLOCKED does not feed the lockout. `AuthInterceptor` runs the passive check BEFORE `isSessionSuperseded` (5 s per-user cache, `site.monitor.session.inactive-cache-ms`). On a hit it strips the session and leaves a TOMBSTONE (`accountInactive` attribute) instead of `invalidate()`, so every tab, every in-flight request and every pod (JDBC store) sees the same signal — don't "fix" this into `invalidate()`. It also deletes the user's remember-me tokens and audits `SESSION_ENDED_INACTIVE`. Deactivation (`UserService.updateUser`, single + bulk) writes the `TERMINATED:` sentinel and deletes the tokens at once. The client (`utils/accountInactive.js`, `AccountInactiveDialog`) shows a non-dismissable 10 s countdown, then goes to `/?session=inactive`. No passive check per endpoint — the central gate is the design. Notifications: `InactiveRecipientGuard` (60 s snapshot, `site.monitor.notify.inactive-cache-ms`) drops contacts linked to passive users (email + webhook) on every contact path. `EmailNotificationService.doSend` drops passive-only addresses; if none remain it logs `SKIPPED: pasif kullanıcı`. Team member lists show passive members last, with a destructive "Pasif" badge; pickers stay active-only.
- **Code login (OTP) + login methods (2026-10-02/03, user request).** `service/otp/*` handles 6-digit single-use codes sent by push or e-mail (default 45 s each, 30–300 s, configurable per channel).
  - **Storage:** the DB holds only `HMAC(SITE_MONITOR_SECRET_KEY sub-key, challengeId:code)` in `login_otp_challenges`. State changes are conditional UPDATEs: 3 attempts by default, single use.
  - **Limits:** counted in a 15-minute window from the DB. The IP limit returns 429. The per-user request limit, the resend cooldown and the failed-verification suspension are SILENT.
  - **No enumeration:** the request endpoint returns the SAME 200 body for eligible, ineligible and unknown users. An ineligible request creates a DECOY row (`user_id=null`, `SUPPRESSED_*`) whose verification behaves exactly like a wrong code. Ineligible means passive, locked, global admin while `allow-global-admins` is off (default), `mustChangePassword` (2026-10-03: use the temporary password), or no target. Delivery is async (`LoginOtpDeliveryService`). Never add a short-circuit (`LoginOtpServiceFlowTest`).
  - **Contact verification (2026-10-03, user request):**
    - **Switches:** `site.monitor.login.otp.push.require-phone` / `.email.require-email`, default ON, GLOBAL_ONLY.
    - **Request:** while a switch is on, the request also carries `phone` / `email`. The code is sent only if the value matches the username's account.
    - **Matching (`OtpContactMatcher`):**
      - phone: digits only; drop `0090`, `90` (when ≥ 10 digits remain) and the trunk `0`; ≥ 10 digits; compare the last 10; constant-time. `AppUser.phone` = AD `mobile`.
      - e-mail: trim + case-insensitive.
    - **Same answer every time:** a mismatch, no usable registered value, or an unknown user returns the SAME 200 plus a decoy (`SUPPRESSED_CONTACT_MISMATCH` / `NO_PHONE` / `NO_TARGET` / `UNKNOWN_USER`).
    - **Blank but required:** 400 `PHONE_REQUIRED` / `EMAIL_REQUIRED` + `field`. Writes no row and uses no IP quota.
    - **Anti-guessing:** `max-contact-mismatches` (1–20, default 5) per username per 15 min → silent `CONTACT_LOCK`. Requests made while locked are not counted. Password login is unaffected.
    - **Timing:** the mismatch count query runs on EVERY request while the switch is on — no short-circuit. Switch OFF ≡ the old behaviour (no query, no `contact` audit key).
    - **Privacy:** the ENTERED value is never stored, logged or audited; audit gets only `contact`=MATCHED/MISMATCH/MISSING/LOCKED/NOT_CHECKED.
    - **Admin view:** adds `coverage` {active_users, with_phone, with_email} from one aggregate query. The UI warns below 80 %.
    - **Gates:** `LoginOtpContactVerificationTest`, `OtpContactMatcherTest`, `LoginOtpCodeNeverLoggedTest.enteredContactNeverLeaks`.
  - **Login statistics + editable OTP push text (2026-10-03, user request):**

    - **UI:** tab `lm_tab=stats`, URL prefix `lm_`. The user directory shows channel badges.
    - **Push text keys:** `site.monitor.login.otp.push.title|message-tr|en`, GLOBAL_ONLY, rules in `OtpPushTemplate`:
      - message: `{kod}` exactly once, plus optional `{sure}` / `{saat}`;

  - **Session:** a successful verification goes through `AuthController.establishSession`, the SAME path as password login (409/forceLogin, remember-me, maintenance, passive, lock, LOGIN method=OTP_*).
  - **The code is never written anywhere:** not to logs, DB columns, `notification_logs`, push delivery rows or audit (`LoginOtpCodeNeverLoggedTest`). `RequestLoggingFilter` skips `/api/login/otp/` bodies. Push goes straight to the gateway (identifier = username, no outbox row). E-mail goes through the funnel with `force=true`.
  - **Lockout:** OTP failures are not `LOGIN_FAILED` and never feed the password lockout.

### Single active session per user
A user holds at most one live session. `UserService` keeps `AppUser.activeSessionId` (newest login wins) plus `lastSeenAt`; the SPA pings `/api/session/ping` (~15s) to keep it fresh. On every `/api/**` request `AuthInterceptor.isSessionSuperseded(user, currentSessionId)` compares the registered id — if it differs, the interceptor invalidates the session, clears the remember-me cookie, and returns **401** (the client then redirects to `/?session=expired`). Login returns **409** when another live session exists; the frontend re-posts with `forceLogin=true` after a confirmation modal. Admin force-logout (`POST /api/admin/system/terminate-session`) sets `activeSessionId` to a `TERMINATED:<uuid>` sentinel that can never match a real session. Two traps: sessions persist in the Spring Session JDBC store but this registry is a single column, so stale ids are cleared at startup (`SessionStoreService.clearStaleActiveSessionMarkers`: jdbc clears only ids with no live `spring_session` row, memory clears all; TERMINATED sentinels always survive); and `activeSessionId = null` means *grandfathered*, not *kicked* — `isSessionSuperseded` returns false for null.

### Opaque user ids (2026-10-08, user decision: "bir kullanıcı başka bir kullanıcının id'sini okuyamasın")
- **Rule:** a GLOBAL admin sees and may send numeric `app_users.id` (byte-identical to before). Everyone else (AUDIT and scoped admins included) sees the opaque `app_users.public_id` (UUID, assigned once, never changes) and may send only that; a numeric user id from them resolves to "not found".
- **Output — one gate:** `config/UserRefResponseAdvice` converts every Jackson response for a non-global viewer into a fresh tree (`UserRefWire`). Values under user-ref KEYS (`user_id`, `manager_id`, `leader_id`, `actor_id`, `author_id`, `editing_user_id`, `contacted_user_id`, … plus camelCase, incl. inside the JSON-text fields `changes`/`detail`/`details`/`snapshot`, and `resource_id` when `resource_type=USER`) become the UUID; an unknown user becomes null. An ambiguous `id` key is NOT rewritten by name: `AppUser.id` carries `@JsonSerialize(UserRef.LongSerializer)` and map rows use `UserRef.of(id)` (user directory, team members, bulk result rows). Outside the gate (storage, logs, global admin) both write a plain number.
- **Input:** every endpoint that takes a user id resolves it with `UserPublicIds.resolve(svc, raw, session)` (path ids are `String`). Controllers get the service as an optional field (`@Autowired(required=false)`) so slice/unit tests without the bean keep the old numeric parsing. Hand-written outputs bypass the gate: the audit CSV/JSON export converts itself (`ExportView`).
- **Adding a field/endpoint:** name a user-id field so its snake_case is in `UserRefWire.KEYS` (or `@JsonIgnore` it), and use `UserRef.of` for a user under an `id` key. The frontend never `Number()`s a user id (`utils/userRef.js`: `userRefValue`, `sameUser`).
- **Gates:** `UserRefCoverageGateTest` (model fields), `UserRefWireTest`, `UserPublicIdsTest`, `UserRefResponseAdviceTest`, `opaqueUserIds.test.jsx`.

### The check pipeline
`SchedulerService.@Scheduled(cron=…)` (default `0 0 * * * *`) acquires the distributed lock and fans out to `CertificateCheckerService`, plus parallel sweeps for `PortCheckerService`, `DnsCheckerService`, `UptimeHttpCheckerService`. Concurrency uses a dedicated `certCheckExecutor` `ThreadPoolTaskExecutor` (bean in `WebConfig`, sized by `EXECUTOR_CORE_SIZE` / `EXECUTOR_MAX_SIZE` / `EXECUTOR_QUEUE_CAPACITY`).

- `CertificateCheckerService` retries **only NETWORK-class** failures once (`CHECK_RETRY=true`). SSL/DNS/CERT errors are never retried — they're real findings.
- TLS handshake fingerprint: `TLS_MODE=browser` forces TLS 1.2 + ALPN `[h2,http/1.1]` so WAFs (Akamai/F5/Imperva) don't RST. Switch to `default` only to debug.
- Outbound proxy: `HTTP_PROXY_HOST`/`PORT` + `NO_PROXY` (suffix match) — applies to OCSP/CRL fetches too.
- `ChainValidationService` does chain + OCSP (primary) + CRL (fallback) via BouncyCastle. CRL responses are Caffeine-cached (`CRL_CACHE_TTL_HOURS`).
- **Revocation reason (2026-10-08, user request: "show the address fields even when empty, remove misleading warnings").**
  - **Backend:** `checkRevocationDetailed` returns status + reason (`RevocationReason`: OCSP, CRL, NO_ENDPOINTS, UNSUPPORTED_SCHEME, UNREACHABLE, NO_ISSUER, NOT_CHECKED, PENDING) + attempts JSON. - **Bulk network outage detection**: if `NETWORK_ERROR_THRESHOLD` (default 0.50) of a run fails with network errors and at least `NETWORK_MIN_ERRORS` (3) failed, individual cert alarms for that run are suppressed and a single `NetworkOutageEvent` + admin email is raised instead. This is intentional — don't "fix" it by always alerting.
- **Per-domain proxy override (`use_proxy`)**: `CertificateInventory.useProxy` (column `use_proxy`, default false) flips a single domain to go through `HTTP_PROXY_HOST/PORT`. `SchedulerService.runCheckForDomains` builds a `domain→forceProxy` map and calls `checkAsync(domain, port, forceProxy)`. Decision: `forceProxy && proxyEnabled() && !shouldBypassProxy(domain)`. Direct outbound stays the default — added so production can route a couple of WAF-quirky domains through the corporate proxy without dragging the rest along.

### Inventory metadata that drives behavior
`CertificateInventory` carries a wide operational schema beyond the cert URL. The fields the rest of the system actually branches on:
- **`tier` (1-4)** — 1: Customer-Facing Prod, 2: Internal Prod, 3: UAT/Pre-Prod, 4: Dev/Sandbox. Drives sort order, criticality badges, and escalation contact selection.
- **`useProxy`** — see above.
- **`teamId` / `ugTeamId`** — primary (SY) and secondary (UG = Uygulama Geliştirici) team ownership for escalation routing.
- **`active`** — `false` = paused (monitoring stops, record kept). **Deletion is PERMANENT (2026-10-07, user decision: "silme işlemi her şekilde kalıcı olsun")** — there is no bin, no restore, no `inventory.purge` permission and no auto-purge setting any more. Every inventory delete (single, bulk, network or manual row) goes through `PermanentDeletionService.deleteInventory`: owner-scoped silent alarm close, then in one transaction the derived Port/DNS monitors + their checks, uptime checks, certificate checks, `latest_checks`, notes + revisions, weak-algorithm exception, certificate diagnostic runs, manual versions and the row (flushed, so the name is free at once). Kept on purpose: closed `alert_events`, audit, `monitor_change_log` (DELETE row, "kalıcı silme"), notification/activity logs, `pinned_cas`. Standalone Port/DNS delete is permanent too (alarms closed, checks deleted, no DNS revival); inventory-derived Port/DNS rows still only pause. `deleted_at` columns stay (raw SQL reads them) but nothing sets them. A deleted name never blocks re-adding (create, rename, import, manual key, suggested key, by-domain all ignore old bin rows). The one-time `DeletedRecordsPurge` (marker `2026-10-07-permanent-delete-bin-purge`, audit `SYSTEM_DELETED_RECORDS_PURGE` with the name lists) purged every legacy bin row at startup. UI: deletes remove the card at once and hide it for 10 min via `utils/recentlyDeleted.js` (per-pod Caffeine caches can return the deleted row from another pod); confirmations say permanent and name the records. Never reintroduce a soft delete or a delete without a confirmation.
- Boolean operational toggles: `externalVendor`, `openshift`, `sslPinning`, `internalCert`, `jksKeystore`, `wafEnabled`, `evCertificate`, `actionRequired`, `transferredToSy`, etc. These are admin-facing flags that show up in InventoryManager and on reports — they don't gate the check pipeline.

When you add a new boolean toggle: append to the `INVENTORY_FLAGS` array in `frontend/src/utils/inventoryFlags.js` (the single source — `inventory-flags-sync.test.jsx` locks its order against the Java side), add the EMPTY default and save-payload entry in `frontend/src/components/inventory/InventoryFormModal.jsx` (the form lives there, not in `InventoryManager.jsx` — it is shared with the dashboard card's Edit/Duplicate buttons), add the diff-builder entry in `AdminController.buildInventoryDiff`, and add the setter call in `updateInventory` — missing the setter is the most common bug (the field "saves" but disappears on reload).

### Request/response trace logging (off by default)
`RequestLoggingFilter` (`@Order(LOWEST_PRECEDENCE - 10)`) can log every HTTP request and response with method, URI, headers, body, status, and duration. It's behind `log.isTraceEnabled()` so the default `com.sitemonitor=DEBUG` level keeps it silent.
- Enable on demand: `logging.level.com.sitemonitor.config.RequestLoggingFilter=TRACE` (env or properties).
- Sensitive values are masked with `*******` via three regex patterns (JSON body / form body / URL query) covering ~60 field-name variants — EN + TR (`password|parola|sifre`, `*_password`, `token|*_token`, `secret|api_key|client_secret`, `private_key`, `session_id|jsessionid`, `pin|otp|mfa_*|verification_code`). Sensitive headers (`authorization`, `cookie`, `x-api-key`, etc.) are masked too.
- Skipped paths: `/health`, `/favicon.ico`, anything under `/assets/` or `/static/`, and common static extensions (`.js .css .map .png .svg .woff2 .ico`).
- Body log is truncated at 2000 chars.

### Escalation & notifications
`EscalationService` selects recipients from `escalation_contacts` based on alert severity (`minAlertLevel`) and org role. `EmailNotificationService` and `WebhookService` (Teams/Slack) deliver. **Recipient routing (team vs escalation)** — two helpers, `isStandaloneMon(alertType)` + `includeManagerContacts(alertType, level)`, govern three paths (initial alert `processConfirmedOutage`, resolution `sendResolutionNotification`, manual resend `reNotify`) and MUST stay consistent across them:
- Standalone monitoring alerts (keyword/ping/http/`TYPE_DOMAIN_EXPIRY`/all `DOMAINMON_*`) resolve the team from `AlertEvent.teamId` (stamped at alarm creation) — **not** the certificate inventory. Standalone domain monitors aren't in `certificate_inventory`, so resolving their team from inventory lost the owning team (the "resend went to the müdür, not the team" bug — fixed by routing all three paths through `event.getTeamId()`).

Another team's manager or contact must never be added, and teamless contacts are never recipients (cannot be created — 400). The old "fall back to global contacts" path used unscoped `findByActiveTrue…` / `findByMinAlertLevel…` queries that returned EVERY team's contacts (cross-team leak, v3.0.0 → v20.89.0); `EscalationContactScopeTest` is the source gate, `EscalationContactLeakTest` the behaviour gate. ### Runtime schema patches (no Flyway/Liquibase)
Schema evolves through two mechanisms, not migrations:
1. `spring.jpa.hibernate.ddl-auto=update` handles new entities and new columns from `@Column` definitions.
2. **`SchedulerService.applySchemaPatches()`** runs idempotent `ALTER TABLE` / `CREATE TABLE` statements at startup via a `patch()` helper that swallows "column/table already exists" errors. This is how `certificate_inventory.use_proxy`, `escalation_contacts.team_id`, `TEXT` widenings, `scheduler_lock`, and the `port_*` / `dns_*` tables landed.

Rule: when you add a column an existing DB might not have, add a `patch()` line. Don't trust `ddl-auto` alone — it won't backfill defaults, rename columns, or widen types.
**Indexes on big tables (2026-10-08): never a blocking `patch("CREATE INDEX …")`.**
- Add them to `service/schema/DeferredIndexBuilder.CATALOG`.
- On PostgreSQL they are built after `ACCEPTING_TRAFFIC` with `CREATE INDEX CONCURRENTLY`, on an off-pool connection.
- One pod builds at a time (advisory lock `SMIDXBLD`). An INVALID leftover is dropped and rebuilt on the next start.
- H2 runs the portable fallback through `patch()`.
- Never drop an index that `@Table(indexes)` still declares — ddl-auto recreates it.
3. **`SchemaPatchRunner`** (`service/schema`, 2026-10-02) executes every `patch()` — same idempotent behaviour, but a REAL failure on PostgreSQL is now a WARN + counted (expected "already exists / does not exist / duplicate" classes stay silent, classified by SQLSTATE so Turkish server messages work), the startup prints one summary line ("Şema yamaları: N uygulandı, M zaten uygulanmış, K başarısız"), and `sitemonitor.schema.patch.failed|applied|noop|locked` gauges expose it. The whole patch run is wrapped in a PostgreSQL session advisory lock (`LOCK_KEY` "SMSCHEMA", wait ≤ 60 s, then proceeds unlocked as before) so two pods never patch concurrently. The `postgres-it` suite (`SchemaPatchPostgresTest`) proves 0 failures on an empty PostgreSQL and on a second start, and that every index/column/constraint a patch names really exists.
4. **`SchemaDdlGuard`** (`service/schema`, 2026-10-09, user decision: "run only if needed, 20 s lock wait"). Statements that run on every boot are skipped when the change is already in the catalog: `ALTER COLUMN … TYPE TEXT|VARCHAR(n)`, `DROP NOT NULL`, `DROP CONSTRAINT IF EXISTS`, `SET (reloptions)`, `CREATE [UNIQUE] INDEX [CONCURRENTLY] IF NOT EXISTS` (also used by the NOC patch classes). A statement that does run uses `SET lock_timeout = '20s'` … `RESET` on the same pooled connection (`CONCURRENTLY` excluded — a timed-out CIC would leave an INVALID index that `IF NOT EXISTS` skips forever); SQLSTATE 55P03 is a WARN, counted as failed with "sonraki açılışta yeniden denenecek". A new unconditional patch FORM must get a recognizer or be written conditionally — `SchemaDdlGuardPostgresTest.everyUnconditionalPatch_isInPlaceAfterBoot` scans the literal `patch("…")` calls and fails otherwise. Locally the postgres-it suite can run on a throwaway cluster (`initdb -U it -A trust` + `pg_ctl -o "-p 55432"` from the local PostgreSQL 16 binaries; delete it afterwards).

### Cert-check thread pool
`WebConfig` registers a `certCheckExecutor` (`ThreadPoolTaskExecutor`) shared by `CertificateCheckerService` / `PortCheckerService` / `DnsCheckerService` / `UptimeHttpCheckerService`. Sized by env:
- `EXECUTOR_CORE_SIZE` (default 20), `EXECUTOR_MAX_SIZE` (50), `EXECUTOR_QUEUE_CAPACITY` (5000). Prod Helm values mirror these (20/50/5000); the rejected-execution handler runs overflow on the caller thread and counts it in `WebConfig.CALLER_RUNS` (System Health → Task Queue).
- **Live tuning (2026-09-10):** the same three keys are in `AppSettingsCatalog` (group `executor`) and editable under Settings → General → Task Pool. `AppSettingsService.save` publishes `AppSettingsChangedEvent`; `ExecutorTuningService` applies core/max/queue to the `TunableThreadPoolTaskExecutor` bean immediately (queue is a `ResizableCapacityQueue`, so capacity changes without restart). Env values are only the boot fallback; a stored override is re-applied on `ApplicationReadyEvent`. Cross-field rule (`core ≤ max`, `queue ≥ 1`) is enforced at save time.
Bump these when inventory grows past a few hundred rows or you see queue backpressure in metrics.

## Things that bite
- **No unbounded loop, regex, retry or wait on untrusted data (2026-10-09, user request: "sonsuz döngüye girmeyecek şekilde geliştirelim").** Every loop driven by network, file, user or DB data needs a cap or a deadline, and the cap must hold even when a timeout cannot interrupt the work.
  - **Regex:** `java.util.regex` ignores `Future.cancel` / interrupts, so a time box never stops a regex. Check length BEFORE any regex on request input. Never put two unbounded quantifiers over overlapping classes around a literal (`[^x]*KEY[^x]*=`), and never use a lazy body plus a backreference (`BEGIN (L)(.*?)END \1`) on uploads. Scan linearly instead: `SecretMask.maskUrlQuery`, `CertificateFileParser.scanPem` / `extract/asn1.js`, `PageCheckerService.globMatches`. In the SPA, `x+$` trailing-punctuation regexes on long text become backward scans. When you rewrite a regex, keep the old one in the test as an oracle (`SecretMaskTest`, `CertificateFileParserPemScanTest`, `linearTextScans.test.js`).
  - **Lists from the outside world** (certificate extensions, ZIP directories, keystore counts, 1xx responses, headers) are deduplicated and capped: `ChainValidationService.MAX_CRL_DOWNLOADS` plus a shared deadline, `RawHttpProbe.MAX_INTERIM_RESPONSES` / `MAX_HEADER_LINES`, `ExtractedUpload.MAX_CERTS` on BOTH upload paths, `ScriptedSafetyRules.MAX_SCRIPT_CHARS` / `MAX_LOOP_HEADERS`, and the browser extractor's PKCS#12 / JCEKS / ZIP caps.
  - **Graphs and chains:** use a visited set plus a depth cap. Exception cause walks use `CauseChain.MAX_DEPTH`; the `CauseChainGuardTest` source gate fails on an unguarded `while/for … getCause()`.
  - **Retry / re-send loops:** claim BEFORE sending (conditional UPDATE), or back off with an attempt cap, and record the give-up in `notification_logs`. Examples: the NOC storm tick (`tickRetryHeld`), the storm daily re-alert (`claimDailyRealert`), the push outbox (`writeRejected`, `sentUnrecorded`).
  - **SPA polling must not overlap itself:** `useVisibleInterval` skips while the previous promise is pending, and one-off polls chain `setTimeout` after the await. Self-reloading paths need a count guard, not only a time guard (`utils/chunkReloadGuard.js`, `utils/sessionExpiry.js`). A boot-time import needs a timeout (`LANG_LOAD_TIMEOUT_MS`).
  - **CI:** every job has `timeout-minutes`, Surefire has `forkedProcessTimeoutInSeconds`, and tests wait with a timeout (`await(n, unit)`, `get(n, unit)`, `assertTimeoutPreemptively`).
- **Names and long text are never clipped (2026-10-10, user report: "takımı yöneten müdürler kısmındaki kayma" — "bu sorunları bir daha yapmayalım").** A person / team name in a 14rem `Badge` with `truncate` lost its START and end (the shadcn Badge centres and hides overflow; `truncate`'s ellipsis does not work on inline-flex). Rules: the Badge base is `justify-center-safe`; no `<Badge>` carries `truncate` (gate `badgeNoTruncate.test.js`, multi-line tags included); show people as plain wrapping text (name · e-mail, `[overflow-wrap:anywhere]`) and list ALL of them (no silent "+N" for recipients); test with real-length AD display names ("Ad Soyad (Bölüm / Unvan)", 60+ chars) and add a Playwright `scrollWidth <= clientWidth` check for every new name/address list.
- **Never mark an `/api/**` response `Cache-Control: public`.** `/api/branding` and `/api/public-stats` were `public, max-age=60`; the NetScaler in front of test/prod cached them with its own TTL, so after a deploy the login page showed the previous version number for minutes and a browser hard refresh could not fix it (2026-09-10). All `/api` responses are `no-store` now (`WebConfigTest.publicEndpoints_areNoStore`); if a public endpoint needs load relief, memoize server-side (see `PublicStatsController.cacheMs`), which also resets on pod restart.

- **CSP has no `'unsafe-inline'` in `script-src` (2026-10-02).** `index.html` loads only the external module and no server HTML has inline scripts; style-src keeps `'unsafe-inline'` (shadcn Chart injects `<style>`, mail previews). Never add an inline `<script>`, an `on*=` attribute or a `javascript:` URL (`WebConfigTest.csp_scriptSrc_hasNoUnsafeInline`).
- **k6 scripts can read pod files — policy gate (2026-10-02, proposal 1).** `ScriptedCheckerService.scanFileReads` flags `open()`, `k6/fs`, local imports and system paths (comment- and string-aware). `site.monitor.scripted.file-read-policy` REPORT (default: save warning + startup summary + `GET /api/admin/scripted/file-read-report`, behaviour unchanged) | BLOCK (save rejected, run returns SKIPPED). Heuristic only — the real fix (k6 in a secret-free sidecar) is still open.
- After any backend change, the user expects: `mvn verify` → if green, `npm run build` (so the frontend is bundled) → restart backend → smoke. Don't skip the restart, login regressions show as 500.
- `start-local.ps1` launches the **packaged jar** (`backend/target/*.jar`), not `spring-boot:run`. `mvn test` does **not** repackage — after a backend code change run `mvn package -DskipTests` (or `verify`) *before* restarting, or the running app serves stale code (e.g. a new response field comes back empty).
- Don't hand-edit `VERSION` / `Chart.yaml` in a release commit — `release.yml` auto-bumps both after every push to `main` (a `chore(release): bump version … [skip ci]` commit). A manual bump makes the next `git pull --rebase` conflict on those files. Let CI own the version; just commit code with a conventional prefix (`feat:` → minor, `fix:` → patch) to drive the bump.
- Frontend always runs on port **5173**. Kill stale processes on 5173/5179 before `npm run dev`.
- Don't put `*` directly in i18n strings for required-field markers — use `<span className="req-star">*</span>` as a separate JSX node. Double-star bug has happened more than once.
- When removing a `useState` or handler, grep for **all** JSX references too — guards in render branches will throw at runtime, not at build time.
- Email credentials in `.env` are committed-locally-only. The Gmail app password in chat history must be rotated before any production deploy (see memory).
- **`.properties` files are read as ISO-8859-1**, not UTF-8. A raw Turkish character in a property *value* gets double-encoded at runtime (`Site Monitör` → UI shows `Site MonitÃ¶r`; a stray default like this even shadows a correct code-side default because Spring property beats the Java fallback arg). Write non-ASCII values as `\uXXXX` escapes (`Site Monit\u00f6r`). `PropertiesEncodingTest` fails the build on raw non-ASCII bytes in non-comment lines. Related trap: javac processes `\u` escapes even inside comments — an illustrative `\uXXXX` in Javadoc is a compile error; write `\\uXXXX`.
- **Renaming a settings-key prefix (e.g. `cert.monitor.*` → `site.monitor.*`) must touch the frontend too.** `AppSettingsCatalog` keys are hardcoded in admin components (`BrandingSettings.jsx` `K()`, `GeneralSettings.jsx` base-url lookup, `HttpMetricsExplorer.jsx` `RETENTION_KEY`) and — easy to miss — i18n labels are built dynamically as `t('general.lbl.' + it.key)`, so the `general.lbl.<full-key>` dict entries never show up when you grep for the construction site. A key mismatch fails *silently*: screens render with empty values / raw-key labels, and unit tests stay green because they mock the API with the same (wrong) keys. `scripts/check-brand.(sh|ps1)` now scans the dotted `cert.monitor` pattern as well — run it after any brand/key rename.
- **The turnip logo (`branding/assets/`) is the permanent default brand mark** (product decision 2026-08-06; brand name is written "SiteMonitor", one word). It ships on every surface — UI (`BrandLogo`), favicon, emails (CID via `BrandMailAssets`), PDFs (`pdfBrand.js`), docs — and only an explicit white-label `branding.logo-data` override may replace it at runtime. **In-app the logo stays neutral green (`ok`) at all times** — same-day user decision: navbar/favicon never turn red with fleet status (status lives in badges/counters; emails DO use severity variants). The status-aware plumbing (`deriveGlobalStatus`, `useStatusFavicon`) is kept ready but unwired. Guards pin this: `frontend/src/test/brand-default.test.jsx` (assets + default renders) and `BrandMailAssetsTest` (classpath assets). If one goes red, restore the default — never loosen the guard. Rules live in `branding/BRAND.md`; regenerate assets only via `branding/tools/make_variants.py`.
- **Helm release rename loses every `--set`-supplied value.** The certmonitor→sitemonitor fresh install silently dropped `HTTP_PROXY_HOST/PORT` (they lived only in the old release's values, not in the repo) — domain registration (RDAP) died with connect timeouts for days. Operational values that prod depends on belong in `environments/master.yaml`, and `docs/DEPLOY_GECIS_PLANI.md` §2.1's checklist must be walked on any release migration. Related trap: the scheduled domain sweep's WHOIS gate must use `whois.anySourceEnabled()` (socket OR `.tr` web-whois) — gating on `enabled()` alone turns off `.tr` web-whois too, while "Sorun Tanıla" (gate-free) keeps working, which hides the bug.
- **Every `*/response-series` endpoint MUST return through `buildResponseSeries(...)`** — never the raw repo `Object[]` rows (Jackson serializes them as arrays, `s.ts` comes back undefined, and the chart screen crashes to the ErrorBoundary; happened 2026-08 with the scripted type). The contract test `MonitoringControllerTest.responseSeries_contract_allEndpoints` counts the mappings reflectively — adding an 8th monitor type without registering it there fails the build by design.
- **Chart components must drop malformed records, not crash**: `ResponseTimeChart` filters entries without a string `ts` before mapping. Keep that defensive filter when refactoring; `ResponseTimeChart.test.jsx` pins it.
- **A derived `deleteBy…` repository method without `@Transactional` fails on every call.** Spring Data only wraps `SimpleJpaRepository`'s own methods (`save`/`delete`/`deleteAll`/`deleteById`); query-derived deletes and `@Modifying` queries get no transaction, and with `open-in-view=false` plus non-transactional controllers the call throws `TransactionRequiredException: No EntityManager with actual transaction available`. Shipped 2026-08-21 as `ScriptedDraftRepository.deleteByOwnerAndMonitorKey`: the controller swallowed it at `log.debug` and the UI announced "draft discarded" without reading the response, so the "unfinished draft" banner came back forever with **zero** log lines. Mock-based service tests can't see this (mocks have no transaction) and `@DataJpaTest` *hides* it (it wraps every test in a transaction) — pin such paths with `@Transactional(propagation = Propagation.NOT_SUPPORTED)`, as `ScriptedRepositoriesTest` now does. `RepositoryWriteTransactionGuardTest` scans every repository interface and fails the build on any writing method that declares neither `@Transactional` nor an entry in its `CALLER_MANAGED_TX` allow-list; adding a line there is a promise that a `@Transactional` caller owns the transaction — verify the caller, don't just silence the test. Return `int`, not `void`, so callers can refuse to report success on 0 rows, and never announce success in the UI without checking `res?.success`.
- **The IDE's Java extension (Eclipse compiler) can rewrite `backend/target/classes`, and its semantics differ from javac.** On 2026-10-02, `x instanceof Number n ? n.longValue() : parseLong(s)` (a `long`/`Long` conditional) passed under javac but threw NPE on a null `Long` when ECJ had recompiled the class, so two NOC tests "failed" with no source change. Write such conditionals with BOTH branches as references (`Long.valueOf(n.longValue())`). Before trusting a backend test failure on unchanged code, re-run after `mvn clean`.
