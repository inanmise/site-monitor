# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Site Monitor — full-stack SSL/TLS certificate monitoring system. Spring Boot 4.1 / Java 25 backend serves a React 18 (Vite 5) SPA; PostgreSQL is the system of record. Single deployable: the React `dist/` is served as static content from the Spring Boot jar in prod. Single VERSION file (`./VERSION`) is authoritative for both backend (`pom.xml` uses `${revision}`; the Docker build passes `-Drevision=$(cat VERSION)`, local builds produce `0.0.0-local`) and frontend (`vite.config.js` reads it at build time).

The UI is bilingual TR/EN; the product language is Turkish, but `storedLang()` (i18n/index.jsx, api/client.js, dateLocale.js) falls back to EN when nothing is stored (since 3be6d0ba) — an open product question, don't change it silently. Most identifiers, log messages, and admin-panel strings are Turkish — keep i18n keys in sync (see `i18n-parity.test.jsx`).

## Architecture — what you need to know across files

### Single-process deployment, multi-replica safe
Frontend ships **inside** the backend jar (`spring.web.resources.static-locations=file:./frontend/dist/,classpath:/static/`). In Kubernetes the same image runs N replicas, so anything stateful must survive pod death and not double-fire:

- **Sessions**: Spring Session JDBC (`spring.session.store-type=jdbc` in `prod` profile) persists to `spring_session` / `spring_session_attributes`. Local dev uses `none` (in-memory).
- **Scheduler distributed lock**: `SchedulerService` self-manages a `scheduler_lock` table (insert/expire by `locked_until`). Only one pod runs the hourly cert sweep. Lock TTL = `SCHEDULER_LOCK_TTL_MINUTES` (10). Admin can force-release via `DELETE /api/admin/system/scheduler-lock`.
- **JPA**: `spring.jpa.open-in-view=false` — entities must be DTO-mapped inside the service transaction; lazy associations after return will throw. Hibernate `ddl-auto=update` is the schema-evolution mechanism (no Flyway/Liquibase).

### Auth — custom interceptor, not Spring Security filter chain
`AuthInterceptor` (registered in `WebConfig`) guards `/api/**`. Login goes through `AuthController`, sessions are HttpSession-based with a remember-me cookie validated by `RememberMeService` (token table: `remember_me_tokens`). Three orthogonal lock states on `AppUser`:
- `lockoutUntil` — temporary progressive lockout (durations: 30s→120s→600s→1800s by default). **Since 2026-09-26 there is no automatic permanent lock** (product decision: an anonymous attacker could permanently lock any account): beyond the last level every further violation repeats the last duration (30 min). Attempts made while locked (`LOGIN_FAILED` with outcome `BLOCKED`) don't count, and the counter uses the canonical username.
- `permanentLock` — legacy state from before 2026-09-26 (and any admin-set lock); admin-only release. Nothing sets it automatically any more.
- `mustChangePassword` — while set, only `/api/me`, `/api/me/change-password`, `/api/login`, `/api/logout` are reachable. Don't add bypass paths.

Spring Security is **not** on the classpath as a filter chain — only `spring-security-crypto` for BCrypt. Don't pull in `spring-boot-starter-security`; it conflicts with the manual interceptor.

### Single active session per user
A user holds at most one live session. `UserService` keeps `AppUser.activeSessionId` (newest login wins) plus `lastSeenAt`; the SPA pings `/api/session/ping` (~15s) to keep it fresh. On every `/api/**` request `AuthInterceptor.isSessionSuperseded(user, currentSessionId)` compares the registered id — if it differs, the interceptor invalidates the session, clears the remember-me cookie, and returns **401** (the client then redirects to `/?session=expired`). Login returns **409** when another live session exists; the frontend re-posts with `forceLogin=true` after a confirmation modal. Admin force-logout (`POST /api/admin/system/terminate-session`) sets `activeSessionId` to a `TERMINATED:<uuid>` sentinel that can never match a real session. Two traps: sessions persist in the Spring Session JDBC store but this registry is a single column, so stale ids are cleared at startup; and `activeSessionId = null` means *grandfathered*, not *kicked* — `isSessionSuperseded` returns false for null.

### Permissions
Per-resource permission model layered on top of `systemRole` (`USER` / `AUDIT` / `ADMIN`) and org role (`PO`/`TECH`/`MANAGER`/`CLEVEL`). Single source of truth: `PermissionCatalog.ALL` — every resource key + allowed actions (`view`/`edit`/`execute`). The Permission Matrix UI renders from this; bootstrap seed is driven from it. **If you add a new resource_key in code, add it to `PermissionCatalog` in the same change** — otherwise the matrix UI won't show it and grants won't bootstrap.

### The check pipeline
`SchedulerService.@Scheduled(cron=…)` (default `0 0 * * * *`) acquires the distributed lock and fans out to `CertificateCheckerService`, plus parallel sweeps for `PortCheckerService`, `DnsCheckerService`, `UptimeHttpCheckerService`. Concurrency uses a dedicated `certCheckExecutor` `ThreadPoolTaskExecutor` (bean in `WebConfig`, sized by `EXECUTOR_CORE_SIZE` / `EXECUTOR_MAX_SIZE` / `EXECUTOR_QUEUE_CAPACITY`).

- `CertificateCheckerService` retries **only NETWORK-class** failures once (`CHECK_RETRY=true`). SSL/DNS/CERT errors are never retried — they're real findings.
- TLS handshake fingerprint: `TLS_MODE=browser` forces TLS 1.2 + ALPN `[h2,http/1.1]` so WAFs (Akamai/F5/Imperva) don't RST. Switch to `default` only to debug.
- Outbound proxy: `HTTP_PROXY_HOST`/`PORT` + `NO_PROXY` (suffix match) — applies to OCSP/CRL fetches too.
- `ChainValidationService` does chain + OCSP (primary) + CRL (fallback) via BouncyCastle. CRL responses are Caffeine-cached (`CRL_CACHE_TTL_HOURS`).
- **Bulk network outage detection**: if `NETWORK_ERROR_THRESHOLD` (default 0.50) of a run fails with network errors and at least `NETWORK_MIN_ERRORS` (3) failed, individual cert alarms for that run are suppressed and a single `NetworkOutageEvent` + admin email is raised instead. This is intentional — don't "fix" it by always alerting.
- **Per-domain proxy override (`use_proxy`)**: `CertificateInventory.useProxy` (column `use_proxy`, default false) flips a single domain to go through `HTTP_PROXY_HOST/PORT`. `SchedulerService.runCheckForDomains` builds a `domain→forceProxy` map and calls `checkAsync(domain, port, forceProxy)`. Decision: `forceProxy && proxyEnabled() && !shouldBypassProxy(domain)`. Direct outbound stays the default — added so production can route a couple of WAF-quirky domains through the corporate proxy without dragging the rest along.

### Inventory metadata that drives behavior
`CertificateInventory` carries a wide operational schema beyond the cert URL. The fields the rest of the system actually branches on:
- **`tier` (1-4)** — 1: Customer-Facing Prod, 2: Internal Prod, 3: UAT/Pre-Prod, 4: Dev/Sandbox. Drives sort order, criticality badges, and escalation contact selection.
- **`useProxy`** — see above.
- **`teamId` / `ugTeamId`** — primary (SY) and secondary (UG = Uygulama Geliştirici) team ownership for escalation routing.
- **`active` / soft-delete** — restore flow uses this; never hard-delete inventory rows from code.
- Boolean operational toggles: `externalVendor`, `openshift`, `sslPinning`, `internalCert`, `jksKeystore`, `wafEnabled`, `evCertificate`, `actionRequired`, `transferredToSy`, etc. These are admin-facing flags that show up in InventoryManager and on reports — they don't gate the check pipeline.

When you add a new boolean toggle: append to the `INVENTORY_FLAGS` array in `frontend/src/utils/inventoryFlags.js` (the single source — `inventory-flags-sync.test.jsx` locks its order against the Java side), add the EMPTY default and save-payload entry in `frontend/src/components/inventory/InventoryFormModal.jsx` (the form lives there, not in `InventoryManager.jsx` — it is shared with the dashboard card's Edit/Duplicate buttons), add the diff-builder entry in `AdminController.buildInventoryDiff`, and add the setter call in `updateInventory` — missing the setter is the most common bug (the field "saves" but disappears on reload).

### Request/response trace logging (off by default)
`RequestLoggingFilter` (`@Order(LOWEST_PRECEDENCE - 10)`) can log every HTTP request and response with method, URI, headers, body, status, and duration. It's behind `log.isTraceEnabled()` so the default `com.sitemonitor=DEBUG` level keeps it silent.
- Enable on demand: `logging.level.com.sitemonitor.config.RequestLoggingFilter=TRACE` (env or properties).
- Sensitive values are masked with `*******` via three regex patterns (JSON body / form body / URL query) covering ~60 field-name variants — EN + TR (`password|parola|sifre`, `*_password`, `token|*_token`, `secret|api_key|client_secret`, `private_key`, `session_id|jsessionid`, `pin|otp|mfa_*|verification_code`). Sensitive headers (`authorization`, `cookie`, `x-api-key`, etc.) are masked too.
- Skipped paths: `/health`, `/favicon.ico`, anything under `/assets/` or `/static/`, and common static extensions (`.js .css .map .png .svg .woff2 .ico`).
- Body log is truncated at 2000 chars.

### Escalation & notifications
`EscalationService` selects recipients from `escalation_contacts` based on alert severity (`minAlertLevel`) and org role. `EmailNotificationService` and `WebhookService` (Teams/Slack) deliver. Every attempt logs to `notification_logs` (SENT/FAILED + error). Re-alert dedupe is daily — `EscalationServiceTest` pins this behaviour; preserve it.

**Recipient routing (team vs escalation)** — two helpers, `isStandaloneMon(alertType)` + `includeManagerContacts(alertType, level)`, govern three paths (initial alert `processConfirmedOutage`, resolution `sendResolutionNotification`, manual resend `reNotify`) and MUST stay consistent across them:
- Standalone monitoring alerts (keyword/ping/http/`TYPE_DOMAIN_EXPIRY`/all `DOMAINMON_*`) resolve the team from `AlertEvent.teamId` (stamped at alarm creation) — **not** the certificate inventory. Standalone domain monitors aren't in `certificate_inventory`, so resolving their team from inventory lost the owning team (the "resend went to the müdür, not the team" bug — fixed by routing all three paths through `event.getTeamId()`).
- **Escalation contacts come ONLY from the alarm's owning team(s)** (product decision 2026-09-28) — single source `EscalationContactScope.forOwners(repo, level, syTeamId, ugTeamId)`: SY and UG each contribute only THEIR OWN contacts (union; one mail per address, webhooks deduped by URL); `teamId == null` → empty, repository never queried. There is **no global fallback**: if a team has no contact at that level the alarm goes to the team's own recipients only (team address / notification group / push) plus a WARN log. Another team's manager or contact must never be added, and teamless contacts are never recipients (cannot be created — 400). The old "fall back to global contacts" path used unscoped `findByActiveTrue…` / `findByMinAlertLevel…` queries that returned EVERY team's contacts (cross-team leak, v3.0.0 → v20.89.0); `EscalationContactScopeTest` is the source gate, `EscalationContactLeakTest` the behaviour gate. The team manager (`teams.manager_id` / LDAP) is NOT an automatic alarm recipient.
- **Level gate (2026-09-19, all monitor types):** `includeManagerContacts` = `!WARNING` — WARNING alarms of standalone monitors are team-only; HIGH/CRITICAL add the owning teams' escalation contacts by their `minAlertLevel`.
- **Standalone vs inventory routing:** standalone monitors (HTTP/Keyword/Ping/Page/Scripted/PageSpeed/Domain and user-added Port/DNS — `standalone` flag / team stamp in context) take their team ONLY from the event/monitor, never from the inventory. Cert alerts, ACCESSIBILITY and inventory-DERIVED Port/DNS (context deliberately unstamped — `SchedulerService.alarmTeamOf`) route like the inventory: SY + UG, each team with its own contacts. Ownerless alarms (no team after full resolution) send nothing on any channel. `TeamAdminService.moveAll` re-stamps OPEN alarm events; a team with open alarms or SY/UG-bound records cannot be deleted (409).
- **Manual "Check now" never raises an alarm** (product decision 2026-09-29, prod incident: a scoped manager's bulk "Check Now (39)" on Synthetic opened alarms and an org-wide storm push). Every trigger endpoint records the result, then evaluates with `handleSweepResults(type, items, manual=true)` — which ONLY runs `reconcileRecoveries`: no new alarm, no confirmation chain, no escalation / re-alert / storm, no suppression bookkeeping; a healthy result may close the open alarm. The next scheduled sweep opens alarms under the normal rules. `evaluateDomainAlarmsNow` is the MANUAL entry; the scheduled critical-domain check uses `evaluateDomainAlarms(m, r, false)`. A manual check also never sends a domain threshold reminder (`DomainExpiryReminderService` runs only from the daily/critical sweeps), never trips `ScriptedAnomalyGuard` (`evaluate(m, res, manual)`; the timeout streak counts scheduled runs only — `scripted_checks.manual`), and never consumes DNS change detection (manual rows are stored with `dns_records.manual = true`; the sweep baseline is `findLatestScheduledSuccessful`; domain registration likewise: manual/live rows and confirmation/recovery rechecks (`checkRecheck`) are stored with `domain_checks.manual = true` (out of band), `DomainCheckerService.checkManual`, scheduled baseline `findLatestScheduledWithData`; the Registration tab reads stored data on open and only runs a live lookup on Refresh; manual DNS rows are never change events). Gates: `ManualCheckNoAlarmTest`, `ManualCheckWiringTest`, `ManualCheckMarkerQueriesTest`. List rows carry `can_check` (= `SessionScope.canOperateTeam` on the effective team) and the UI counts/queues only those.
- **Alert storms are TEAM-scoped** (same decision): scope key `TEAM:<id>` (per-group: `TEAM:<id>|GROUP:<g>`); the window count, threshold (COUNT, or PERCENT of the team's own active monitors — `totalActiveMonitorsForTeam`), root cause and every notification come from the owning team's events only; ownerless events never storm. Each dispatch (SY, and UG for co-owned inventory rows) shows ONLY its own count/name/root cause — there is no "Tüm monitörler" / org-wide storm; legacy `ACCOUNT`/group storms are disbanded by `lifecycleSweep`. Storm push level = the highest member level (`stormPushLevel`), never wider than the individual alarms' audience. The threshold counts DISTINCT targets (`distinctTargets` — one host's ACCESSIBILITY/PORT/DNS/HTTP alerts are one target); PERCENT has an absolute floor of 3 (`PERCENT_MIN_TARGETS`). Legacy storms stay inert for `site.monitor.storm.legacy-retire-grace-minutes` (15) after start-up, then `retireLegacy` moves still-down members into their team storm silently (above threshold) or releases them as already notified (`releaseFromStormAsNotified`) — never individual INITIALs; the recovery of recovered members goes only to their own team. Gate: `StormTeamIsolationTest`.
- **Storms have a bounded lifetime and every silent decision leaves a trace (2026-09-30, prod incident: the SY team's 3 permanently failing synthetic tests kept a team storm above the hysteresis floor forever, so `StormService.evaluate` attached EVERY new DOWN alarm of that team silently — no email, push, webhook, NOC, `notification_logs` row or push-decision row; the UI showed "0 notifications").** `alert_storms.last_member_at` is stamped at creation and on every attach; once `site.monitor.storm.quiet-minutes` (default 5, 5–1440, Settings → Alert Storm → Quiet Window) pass without a new member the storm is SEALED: `evaluate` sends individually instead of attaching and `lifecycleOne` resolves it regardless of still-down count. On resolve, still-down members announced in the storm's last mail (`createdAt ≤ storm.lastReAlertAt`) are released as notified (`releaseFromStormAsNotified`), unannounced ones are unlinked (`lastReAlertAt=null` → individual INITIAL on the next sweep). The SUPPRESSED branch of `processConfirmedOutage` calls `recordStormSuppression` (log row trigger `STORM`, status `SKIPPED: fırtına #N …`, push row `SKIPPED_STORM`); the ownerless gate writes `SKIPPED: takım yok` + `SKIPPED_NO_TEAM`; `sendCombinedAlert` no longer returns early when mail is skipped and logs `SKIPPED: alıcı yok` / `SKIPPED: e-posta kanalı kapalı`; storm mails are logged per member alarm (`STORM_INITIAL` / `STORM_REALERT` / `STORM_RESOLVE`). The alert list/detail show a `StormBadge` (`storm_id`) and the timeline renders the `STORM` row as "notification handed over to the storm". `StormSuppressionBackfill` writes the trace once for historical storm members with no log rows. Never reintroduce a silent, unlogged suppression path — a notification that is not sent must say why in `notification_logs`. Gates: `StormSealingTest`, `EscalationServiceTest.processConfirmedOutage_stormSuppressed_leavesTrace`, `StormSuppressionBackfillTest`, `AlertHistoryStorm.test.jsx`.
- **Storm observability (2026-09-30).** `alert_storms` freezes an opening snapshot (`team_id`, `group_name`, `threshold_unit/value/effective`, `window_minutes`, `quiet_minutes`, `targets_at_open`, `peak_targets`, `trigger_event_id`) IN the atomic promotion INSERT (`insertStormIfAbsent(…, OpenSnapshot)`, 17 bind args, the first 7 keep their order — a separate UPDATE let a concurrent lifecycle `save` null them) and a `resolve_reason` (`FLOOR`/`SEALED`/`DISABLED`/`LEGACY_RETIRE`). Membership is durable in `alert_storm_members` (`AlertStormMember`: join kind TRIGGER/PEER/ATTACH/LEGACY, `announced_at`, leave kind RECOVERED/NOTIFIED/UNLINKED/MOVED/RELEASED) because `alert_events.storm_id` is cleared on close. Writes are JDBC on the alarm path and must stay O(1) round trips per event: opening = one `batchUpdate(SQL_MEMBER_INSERT)` (`ON CONFLICT DO NOTHING`, no exists-check), attach = one INSERT, announce = one UPDATE (IN chunks of 500), close = one `batchUpdate(SQL_MEMBER_LEFT)`; every recording call is try/catch — observability must never change or delay a notification decision. The in-flight lifecycle refresh uses a targeted `UPDATE … member_count, peak_targets = GREATEST(…)` instead of `stormRepo.save` (a stale entity save rewound `last_member_at`). Read side: `StormStatusService` + `StormStatusController` (`GET /api/monitoring/storm/status|history|analytics|{id}`, gate `alerts.read/view`, scope like `TodayPanelController.openAlerts`; `status` is memoized 10 s per scope key, `?fresh=1` bypasses; per-team active monitor counts come from ONE grouped query `StormService.activeMonitorsByTeam()` (60 s), triggers/live members are batch-loaded — never add a per-team or per-storm query to these polled paths) → `?tab=storms` (`StormStatusPage`, URL prefix `sf_`) and the Settings → Alert Storm live panel (`StormLivePanel`). Adding a storm column/table: patch it in `applySchemaPatches`, append new INSERT columns at the END (`StormTeamIsolationTest` reads the bind args positionally), register retention (`alert-storm-members-orphan`). Gates: `StormObservabilityRecordTest`, `StormStatusServiceTest`, `StormStatusControllerTest`, `StormObservabilityQueriesTest`, `StormStatusPage.test.jsx`, `StormLivePanel.test.jsx`.
- **Auto-close is reconciliation, not a transition** (2026-09-29, "ghost alarm" fix): `MonitoringOutageService.handleSweepDomain` decides per sweep from "open alarm in DB + current result healthy"; every healthy result increments a consecutive counter and N consecutive healthy sweeps close the alarm (atomic, idempotent; the active recovery chain is only a fast path, stuck chains are replaced). Fleet-wide outage suppression (`noteSuppression`) and `site.monitor.<type>.alert-enabled=false` may ONLY stop new alarms / confirmation / re-alerts — never recovery (`reconcileRecoveries`). A sibling monitor sharing the event key (`domain|alertType`) that is still DOWN keeps the alarm open. `DNS_CHANGED` / `DOMAINMON_CHANGED` close manually by design. Cert alarms reconcile even under outage suspicion / disabled expiry alerts (`resolveVerifiedStaleCertAlerts`).
- Email **content** (detail table) for `DOMAINMON_*` is rebuilt fresh from the latest `DomainCheck` via `reconstructDomainContext(domain)` — `latestCheckRepo` is cert-only and returns nothing for a domain monitor, which is why resend/resolution mails looked empty before.
- Domain expiry alarm **severity** must mirror the card status tiers (`DomainCheckerService`: `days≤crit→CRITICAL`, `crit<days≤warn→WARNING`) — set in `SchedulerService.addDomainSweepItems`. Don't reintroduce a flat `HIGH`.
- **Noise analysis suggestions are a code catalogue (2026-10-01).** `AlertNoiseService` classifies noisy targets/teams and emits `suggestions[]` with codes from `AlertNoiseSuggestion` (thresholds are the service's `static final` constants — one place); the UI renders `t('noise.sug.<CODE>.title|body', ...params)` and turns `action.kind` (`open_monitor|open_alerts|open_settings|open_maintenance`) into a button (`alerts/noiseModel.js#runSuggestionAction`). Adding a code means adding TR + EN `noise.sug.<CODE>.title` / `.body` in the same change — `AlertNoiseSuggestionI18nGateTest` reads `frontend/src/i18n/index.jsx` and fails the backend build otherwise (the frontend used-keys gate cannot see the dynamic key). The response is additive: never rename the legacy fields (`top`, `flapping`, `heat`, `series`, `by_type`, KPI totals) — the panel and its old test depend on them.

- **Quiet hours are opt-in and never silent (2026-10-01, approved proposal 15).** Team window = `teams.quiet_start/quiet_end/quiet_days/quiet_min_level` (HH:mm Europe/Istanbul, may cross midnight, days = the day the window STARTS, null = no window). Rule lives in `QuietHours` (also used for personal push quiet hours on `app_users.push_quiet_*`). `EscalationService.sendCombinedAlert` defers only INITIAL/ESCALATION/DAILY_REALERT (`TeamQuietHoursService.DEFERRABLE_TRIGGERS`) for the owning team(s) in their window: default only WARNING, `quiet_min_level=CRITICAL` also HIGH, CRITICAL never; MANUAL resend, NOC and storm mails are not deferred. Every deferral writes `notification_logs` trigger `QUIET_HOURS` + `SKIPPED: sessiz saat …` and a `quiet_digest_items` row (UNIQUE alarm×team×window); push gets `SKIPPED_TEAM_QUIET` via the `quiet_deferred` ctx flag. A resolution whose OPENING was deferred and whose digest hasn't gone is folded into the digest. `QuietDigestService` (minute job, `scheduler_lock` `quiet-digest`, claim-token = at-most-once) mails one digest per team per recipient set, logs `QUIET_DIGEST` per alarm and restamps `last_re_alert_at` of still-open alarms; timed escalation steps are held while quiet/pending and `QUIET_DIGEST` is a step anchor. Settings come from a 60 s in-memory cache (no per-alarm query; other pods see a change within 60 s). Gates: `QuietHoursEscalationTest` (no-config ≡ today on every path), `QuietDigestServiceTest`, `EscalationStepQuietHoldTest`, `UserPushQuietHoursTest`.

All routing rules still apply (owning teams only, level gate, WARNING-standalone → no contacts, ownerless → nothing); ack / storm / maintenance / fleet-outage skips write `ESCALATION_STEP` + `SKIPPED: …`. Re-alert override keys `site.monitor.realert.<family>-minutes` (0 = global interval; 15–10080). Gates: `EscalationStepRegressionTest` (no-config ≡ today incl. notification_logs), `EscalationStepServiceTest`, `ReAlertIntervalOverrideTest`.
- **Runbook note + incident link (2026-10-02, proposal 14).** If a non-blank `MonitorGuide` exists for the alarm's type+target, `sendCombinedAlert` appends a "Ne yapılmalı" block (markdown → escaped plain text, ≤ 1000 chars email / ≤ 300 webhook) — INITIAL/ESCALATION/re-alert/manual resend and the timed step only; resolution, storm, NOC and personal push are unchanged. Without a guide the output is byte-identical (`RunbookNoteNotificationTest`). - **HTTP advanced request + `HTTP_SLOW` (2026-10-02, proposal 9).** `http_monitors` gained encrypted `custom_headers_enc` (global admin only, like Keyword/PageSpeed), `basic_auth_user/pass_enc`, `request_body`/`request_content_type` (POST only, ≤ 64 KB), `json_path`/`json_expected` (small resolver `service/http/JsonAssertion`, failure = HTTP_DOWN with "JSON doğrulaması başarısız: …") and `slow_response_enabled`/`slow_threshold_ms` → new alert type `HTTP_SLOW` (wired like `KEYWORD_SLOW`; never a storm member). With no advanced field set the old 7-argument `HttpCheckerService.check` runs and the request is byte-identical (`HttpRequestBuildTest`); headers/auth/body are dropped on cross-host redirects. - **Push outbox is claimed, not just read (2026-10-02, proposal 3).** `UserPushService.drainOutbox` leases due PENDING rows with `claimDue` (writes a per-run unique lease stamp into `next_attempt_at`, ≥ 2 min) and sends only `findByIdInAndNextAttemptAtOrderByIdAsc(ids, lease)` — two pods never send the same push; a dead pod's lease expires and the row is retried. If the claim query fails the old read-and-send path runs.

**Critical-domain second daily check** — `SchedulerService.runCriticalDomainChecks()` (`@Scheduled` cron `DOMAIN_CRITICAL_CHECK_CRON`, default `0 0 16 * * *` Europe/Istanbul; separate `scheduler_lock` key `domain-critical-sweep`) re-checks ONLY active domains whose last check `days_remaining ≤ DOMAIN_CRITICAL_CHECK_THRESHOLD_DAYS` (default 7). It calls the same `evaluateDomainAlarmsNow`, so a same-day renewal auto-closes the open `DOMAINMON_EXPIRY` alarm without waiting for the next morning sweep, while the daily re-alert dedupe still suppresses a second notification for a still-critical domain. Toggle with `DOMAIN_CRITICAL_CHECK_ENABLED`. Two same-day checks intentionally write two `domain_checks` rows.

### Runtime schema patches (no Flyway/Liquibase)
Schema evolves through two mechanisms, not migrations:
1. `spring.jpa.hibernate.ddl-auto=update` handles new entities and new columns from `@Column` definitions.
2. **`SchedulerService.applySchemaPatches()`** runs idempotent `ALTER TABLE` / `CREATE TABLE` statements at startup via a `patch()` helper that swallows "column/table already exists" errors. This is how `certificate_inventory.use_proxy`, `escalation_contacts.team_id`, `TEXT` widenings, `scheduler_lock`, and the `port_*` / `dns_*` tables landed.

Rule: when you add a column an existing DB might not have, add a `patch()` line. Don't trust `ddl-auto` alone — it won't backfill defaults, rename columns, or widen types.
3. **`SchemaPatchRunner`** (`service/schema`, 2026-10-02) executes every `patch()` — same idempotent behaviour, but a REAL failure on PostgreSQL is now a WARN + counted (expected "already exists / does not exist / duplicate" classes stay silent, classified by SQLSTATE so Turkish server messages work), the startup prints one summary line ("Şema yamaları: N uygulandı, M zaten uygulanmış, K başarısız"), and `sitemonitor.schema.patch.failed|applied|noop|locked` gauges expose it. The whole patch run is wrapped in a PostgreSQL session advisory lock (`LOCK_KEY` "SMSCHEMA", wait ≤ 60 s, then proceeds unlocked as before) so two pods never patch concurrently. The `postgres-it` suite (`SchemaPatchPostgresTest`) proves 0 failures on an empty PostgreSQL and on a second start, and that every index/column/constraint a patch names really exists.

### Cert-check thread pool
`WebConfig` registers a `certCheckExecutor` (`ThreadPoolTaskExecutor`) shared by `CertificateCheckerService` / `PortCheckerService` / `DnsCheckerService` / `UptimeHttpCheckerService`. Sized by env:
- `EXECUTOR_CORE_SIZE` (default 20), `EXECUTOR_MAX_SIZE` (50), `EXECUTOR_QUEUE_CAPACITY` (5000). Prod Helm values mirror these (20/50/5000); the rejected-execution handler runs overflow on the caller thread and counts it in `WebConfig.CALLER_RUNS` (System Health → Task Queue).
- **Live tuning (2026-09-10):** the same three keys are in `AppSettingsCatalog` (group `executor`) and editable under Settings → General → Task Pool. `AppSettingsService.save` publishes `AppSettingsChangedEvent`; `ExecutorTuningService` applies core/max/queue to the `TunableThreadPoolTaskExecutor` bean immediately (queue is a `ResizableCapacityQueue`, so capacity changes without restart). Env values are only the boot fallback; a stored override is re-applied on `ApplicationReadyEvent`. Cross-field rule (`core ≤ max`, `queue ≥ 1`) is enforced at save time.
Bump these when inventory grows past a few hundred rows or you see queue backpressure in metrics.

### Timezone
Backend stores timestamps as UTC (audit, alerts, notifications). Log timestamps are localized via `LOG_TIMEZONE` (default `Europe/Istanbul`). Frontend formats with `date-fns` against Europe/Istanbul (UTC+3, no DST). When doing date arithmetic, use `setUTC*` to avoid the 3-hour drift trap.

## When adding tests

- **Backend**: mirror the package layout under `src/test/java/`. Prefer `@ExtendWith(MockitoExtension.class)` for unit isolation; reach for `@SpringBootTest` only when you need full context (currently exactly one: `SqlSamplesIntegrationTest`). H2 is on the test classpath.
- **Frontend**: place `.test.jsx` next to the component file under `src/test/`. Use `test-utils.jsx#render()`. Add new i18n keys to **both** `TR` and `EN` in the same change or the parity test will fail.

## CI gates (`.github/workflows/`)

- `ci.yml` — Java 25 + Node 24. Backend runs `mvn -B clean verify` (uploads Surefire + Jacoco artifacts). Frontend runs `npm ci` → `lint --if-present` → `test --silent -- --run` → `build` → `npm audit --audit-level=high --omit=dev` (non-blocking). Helm-lint runs against all three env values files.
- `docker-build.yml` — multi-arch image build + Trivy scan (HIGH/CRITICAL, currently report-only).
- `release.yml` — runs on `main`; detects bump from conventional commit prefix (`feat:` → minor, `fix:` → patch, `BREAKING CHANGE` → major), writes `VERSION`, publishes Helm chart. Does **not** re-run tests; trusts `ci.yml`.
- `ci.yml` job `backend-postgres-it` (2026-10-02, gating): `postgres:16` service + `mvn -B -Ppostgres-it test` with `IT_DB_URL/USER/PASSWORD` and `IT_DB_REQUIRED=true`. The `@PostgresIntegration` suite (tag `postgres`, excluded from the default surefire run) refuses a non-empty database, boots the context twice and asserts 0 failed schema patches, real indexes, PostgreSQL-only SQL (ON CONFLICT, LATERAL, claims, rollup upserts) and the polled-screen queries. Locally: point `IT_DB_*` at an EMPTY throwaway database (the dev DB user has no CREATEDB).
- `docker-build.yml` job `image-boot-test` (non-gating): pulls the pushed image, runs it like Helm (prod profile, read-only root FS, 1 GiB) against a postgres service and runs `scripts/image-boot-check.sh` (health, 401 gate, schema-patch gauges, no ERROR / BAŞARISIZ in the log).

## Things that bite
- **Never mark an `/api/**` response `Cache-Control: public`.** `/api/branding` and `/api/public-stats` were `public, max-age=60`; the NetScaler in front of test/prod cached them with its own TTL, so after a deploy the login page showed the previous version number for minutes and a browser hard refresh could not fix it (2026-09-10). All `/api` responses are `no-store` now (`WebConfigTest.publicEndpoints_areNoStore`); if a public endpoint needs load relief, memoize server-side (see `PublicStatsController.cacheMs`), which also resets on pod restart.

- **CSP has no `'unsafe-inline'` in `script-src` (2026-10-02).** `index.html` loads only the external module and no server HTML has inline scripts; style-src keeps `'unsafe-inline'` (shadcn Chart injects `<style>`, mail previews). Never add an inline `<script>`, an `on*=` attribute or a `javascript:` URL (`WebConfigTest.csp_scriptSrc_hasNoUnsafeInline`).
- **k6 scripts can read pod files — policy gate (2026-10-02, proposal 1).** `ScriptedCheckerService.scanFileReads` flags `open()`, `k6/fs`, local imports and system paths (comment- and string-aware). `site.monitor.scripted.file-read-policy` REPORT (default: save warning + startup summary + `GET /api/admin/scripted/file-read-report`, behaviour unchanged) | BLOCK (save rejected, run returns SKIPPED). Heuristic only — the real fix (k6 in a secret-free sidecar) is still open.
- After any backend change, the user expects: `mvn verify` → if green, `npm run build` (so the frontend is bundled) → restart backend → smoke. Don't skip the restart, login regressions show as 500.
- `start-local.ps1` launches the **packaged jar** (`backend/target/*.jar`), not `spring-boot:run`. `mvn test` does **not** repackage — after a backend code change run `mvn package -DskipTests` (or `verify`) *before* restarting, or the running app serves stale code (e.g. a new response field comes back empty).
- Don't hand-edit `VERSION` / `Chart.yaml` in a release commit — `release.yml` auto-bumps both after every push to `main` (a `chore(release): bump version … [skip ci]` commit). A manual bump makes the next `git pull --rebase` conflict on those files. Let CI own the version; just commit code with a conventional prefix (`feat:` → minor, `fix:` → patch) to drive the bump.
- Frontend always runs on port **5173**. Kill stale processes on 5173/5179 before `npm run dev`.
- Don't put `*` directly in i18n strings for required-field markers — use `<span className="req-star">*</span>` as a separate JSX node. Double-star bug has happened more than once.
- When removing a `useState` or handler, grep for **all** JSX references too — guards in render branches will throw at runtime, not at build time.
- Email credentials in `.env` are committed-locally-only. The Gmail app password in chat history must be rotated before any production deploy (see memory).
- **`.properties` files are read as ISO-8859-1**, not UTF-8. A raw Turkish character in a property *value* gets double-encoded at runtime (`Site Monitör` → UI shows `Site MonitÃ¶r`; a stray default like this even shadows a correct code-side default because Spring property beats the Java fallback arg). Write non-ASCII values as `\uXXXX` escapes (`Site Monit\u00f6r`). `PropertiesEncodingTest` fails the build on raw non-ASCII bytes in non-comment lines. Related trap: javac processes `\u` escapes even inside comments — an illustrative `\uXXXX` in Javadoc is a compile error; write `\\uXXXX`.
- **Renaming a settings-key prefix (e.g. `cert.monitor.*` → `site.monitor.*`) must touch the frontend too.** `AppSettingsCatalog` keys are hardcoded in admin components (`BrandingSettings.jsx` `K()`, `GeneralSettings.jsx` base-url lookup, `HttpMetricsExplorer.jsx` `RETENTION_KEY`) and — easy to miss — i18n labels are built dynamically as `t('general.lbl.' + it.key)`, so the `general.lbl.<full-key>` dict entries never show up when you grep for the construction site. A key mismatch fails *silently*: screens render with empty values / raw-key labels, and unit tests stay green because they mock the API with the same (wrong) keys. `scripts/check-brand.(sh|ps1)` now scans the dotted `cert.monitor` pattern as well — run it after any brand/key rename.
- **The turnip logo (`branding/assets/`) is the permanent default brand mark** (product decision 2026-08-06; brand name is written "SiteMonitor", one word). It ships on every surface — UI (`BrandLogo`), favicon, emails (CID via `BrandMailAssets`), PDFs (`pdfBrand.js`), docs — and only an explicit white-label `branding.logo-data` override may replace it at runtime. **In-app the logo stays neutral green (`ok`) at all times** — same-day user decision: navbar/favicon never turn red with fleet status (status lives in badges/counters; emails DO use severity variants). The status-aware plumbing (`deriveGlobalStatus`, `useStatusFavicon`) is kept ready but unwired. Guards pin this: `frontend/src/test/brand-default.test.jsx` (assets + default renders) and `BrandMailAssetsTest` (classpath assets). If one goes red, restore the default — never loosen the guard. Rules live in `branding/BRAND.md`; regenerate assets only via `branding/tools/make_variants.py`.
- **Helm release rename loses every `--set`-supplied value.** The certmonitor→sitemonitor fresh install silently dropped `HTTP_PROXY_HOST/PORT` (they lived only in the old release's values, not in the repo) — domain registration (RDAP) died with connect timeouts for days. Operational values that prod depends on belong in `environments/master.yaml`, and `docs/DEPLOY_GECIS_PLANI.md` §2.1's checklist must be walked on any release migration. Related trap: the scheduled domain sweep's WHOIS gate must use `whois.anySourceEnabled()` (socket OR `.tr` web-whois) — gating on `enabled()` alone turns off `.tr` web-whois too, while "Sorun Tanıla" (gate-free) keeps working, which hides the bug.
- **Every `*/response-series` endpoint MUST return through `buildResponseSeries(...)`** — never the raw repo `Object[]` rows (Jackson serializes them as arrays, `s.ts` comes back undefined, and the chart screen crashes to the ErrorBoundary; happened 2026-08 with the scripted type). The contract test `MonitoringControllerTest.responseSeries_contract_allEndpoints` counts the mappings reflectively — adding an 8th monitor type without registering it there fails the build by design.
- **Chart components must drop malformed records, not crash**: `ResponseTimeChart` filters entries without a string `ts` before mapping. Keep that defensive filter when refactoring; `ResponseTimeChart.test.jsx` pins it.
- **A derived `deleteBy…` repository method without `@Transactional` fails on every call.** Spring Data only wraps `SimpleJpaRepository`'s own methods (`save`/`delete`/`deleteAll`/`deleteById`); query-derived deletes and `@Modifying` queries get no transaction, and with `open-in-view=false` plus non-transactional controllers the call throws `TransactionRequiredException: No EntityManager with actual transaction available`. Shipped 2026-08-21 as `ScriptedDraftRepository.deleteByOwnerAndMonitorKey`: the controller swallowed it at `log.debug` and the UI announced "draft discarded" without reading the response, so the "unfinished draft" banner came back forever with **zero** log lines. Mock-based service tests can't see this (mocks have no transaction) and `@DataJpaTest` *hides* it (it wraps every test in a transaction) — pin such paths with `@Transactional(propagation = Propagation.NOT_SUPPORTED)`, as `ScriptedRepositoriesTest` now does. `RepositoryWriteTransactionGuardTest` scans every repository interface and fails the build on any writing method that declares neither `@Transactional` nor an entry in its `CALLER_MANAGED_TX` allow-list; adding a line there is a promise that a `@Transactional` caller owns the transaction — verify the caller, don't just silence the test. Return `int`, not `void`, so callers can refuse to report success on 0 rows, and never announce success in the UI without checking `res?.success`.
- When output contains mojibake (`Ã¶`, `ÃÂ¶`…), don't dismiss it as a console/terminal display artifact — verify the raw bytes end-to-end (`curl … | od -c`, check DB with `octet_length`, check the compiled class) before concluding. The 2026-08 branding bug shipped because the double-encoding was visible in a smoke output and got waved off as console encoding.
